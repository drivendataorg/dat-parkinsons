# Stages 00-03: data staging, folds, registered features and the linear members

Scripts: `pipeline/00_stage_data.sh`, `pipeline/01_folds.sh`, `pipeline/02_features.sh`,
`pipeline/03_linear.sh`. Conventions shared by every stage (interpreter, environment
variables, logs, the original development tree) are described in [README.md](README.md).

## Purpose

These four stages turn the competition download into the shared cross-validation folds,
the registered hand-crafted feature tables and the two L1 logistic regression members of
the stack:

- `lin`: 235 feature columns, C = 0.2
- `lin4`: 94 feature columns, C = 1.0

Later stages read three groups of their outputs:

- `outputs/oof_feat3_m2fnh.csv` is the stacker's `--feat` input (stage 08).
- `submission_src/assets/linear_lin.json` and `linear_lin4.json` go into the v17 archive as
  `assets/linear_lin.json` and `assets/linear_lin4.json` (stages 08 and 09).
- `outputs/features_v13_m2f.csv`, `features_v13_m2fnh.csv`, `features_v4_m2fnh.csv` and
  `folds.csv` feed the TabICL block (stage 07).

On the development machine every file regenerated by these stages was byte-identical
(sha256) to the archived original. This includes the feature tables, whose registration
ran on the Apple GPU (MPS).

## Commands

From the repository root:

```bash
bash pipeline/00_stage_data.sh path/to/niftis_<id>.zip path/to/train_labels_<id>.csv
bash pipeline/01_folds.sh
bash pipeline/02_features.sh            # optional argument: path/to/template_v6.npy
bash pipeline/03_linear.sh
```

`00_stage_data.sh` without arguments only verifies an existing staging. `train_all.sh`
calls it that way, so the data must be staged first (README, "Setup").
`02_features.sh` takes the frozen registration template from
`inference/assets/template_v6.npy` unless a path is given, so `scripts/install_weights.py`
must have run before it.

| script | what it runs | original command it reproduces |
|---|---|---|
| `00_stage_data.sh` | `unzip -q -o -j <zip> '*.nii.gz' -d data/raw/niftis` and `cp <labels> data/raw/labels.csv` | Not recorded. The original project kept the same two items in `data-demo/`. |
| `01_folds.sh` | `cd src && python folds.py` | The same command (`src/folds.py` entry point). |
| `02_features.sh` | template staging, `make_regfeat32.py`, `src/filter_feature_tables.py --tag m2` | The 2026-09-02 "m2" feature build plus two one-off filter steps (below). |
| `03_linear.sh` | `src/linear_oof.py`, then `train_final3.py --export`, then a column-set assertion | A one-off OOF step of 2026-09-03 and line 17 of `tools/build_clean.sh`. |

### 00_stage_data.sh

The script unpacks the scans flat into `data/raw/niftis/<uid>.nii.gz` and copies the label
file byte for byte to `data/raw/labels.csv`. It compares the sha256 of both downloads with
the files used during the competition (zip `87a17ccd…`, labels `1660731b…`) and prints a
warning on a mismatch without stopping. When 1,362 scans and 1,362 label rows are already
present, it only re-checks the counts. It exits 1 when the label header is not
`uid,is_pathologic`, when a count is wrong or when a labelled uid has no scan. It prints
counts and hashes only. `DAT_DATA_DIR` moves the staging directory.

### 01_folds.sh

`src/folds.py` runs `StratifiedKFold(n_splits=5, shuffle=True, random_state=42)` over the
rows of `labels.csv` in file order. When `outputs/folds.csv` already exists with the same
uid set and fold count, the script leaves it unchanged. Deleting the file forces a new
split. Every out-of-fold (OOF) member (lin, lin4, the CNNs, the stacker) uses this file.

### 02_features.sh

1. Copies the template to `outputs/template_v6.npy` if that file is absent and checks its
   sha256 against `4d3629d5a06aadd8d638e2333f37169de5a460524be3314944553b23fb2b0672`
   (exit 1 on a mismatch). Copies `configs/feature_columns/features_v4_reg7f.header.csv` to
   `outputs/features_v4_reg7f.csv`.
2. Runs the original feature build. The original command was:

   ```bash
   cd src && DAT_MASK_V2=1 KMP_DUPLICATE_LIB_OK=TRUE PYTORCH_ENABLE_MPS_FALLBACK=1 \
     OMP_NUM_THREADS=1 REFEAT_JOBS=4 python -u make_regfeat32.py \
     --rich features_v13_m2.csv --narrow features_v4_m2.csv --narrow-like features_v4_reg7f.csv
   ```

   The pipeline runs it with the same arguments and variables, except that `REFEAT_JOBS`
   defaults to 3 (an exported `REFEAT_JOBS` overrides it) and the log goes to
   `outputs/logs/regfeat_m2.log`. `make_regfeat32.py` preprocesses each NIfTI in float32
   on the CPU with the disc guard on (`DAT_MASK_V2=1`), registers the 48³ crop rigidly
   (6 degrees of freedom) to the template on MPS, CUDA or CPU in that order of preference,
   rejects a fit that rotates more than 90° or reaches NCC below 0.30, and extracts the
   rich (240) and narrow (98) feature sets.
3. Runs `python src/filter_feature_tables.py --tag m2`, which writes the m2f and m2fnh
   tables.

### 03_linear.sh

The script exports `KMP_DUPLICATE_LIB_OK=TRUE PYTORCH_ENABLE_MPS_FALLBACK=1
OMP_NUM_THREADS=3 HF_HUB_OFFLINE=1`, the variables `tools/build_clean.sh` exported.

1. `python src/linear_oof.py` writes `outputs/oof_feat3_m2fnh.csv`.
2. The original export, line 17 of `tools/build_clean.sh` (v12b build, repeated with
   byte-identical results for v13b, v13c and v14c):

   ```bash
   cd src && python -u train_final3.py --rich-features features_v13_m2fnh.csv \
     --narrow-features features_v4_m2fnh.csv --export
   ```

   `train_final3.py` fits a `FeatPrep` transform (median imputation, log1p, clipping at the
   0.5 and 99.5 percentiles, standardisation) and a liblinear L1 `LogisticRegression`
   (C = 0.2 for lin, 1.0 for lin4, `max_iter` 8000, `random_state` 0) on all 1,362 rows.
   It also fits LightGBM (5 seeds of 700 rounds) and an MLP bag, which v17 does not ship.
   The script checks that the log contains `exported: L1 kept` and exits 1 otherwise.
3. The assertion that followed the export in `build_clean.sh`: `linear_lin.json` has 235
   features, `linear_lin4.json` has 94, and neither contains `head_ml` or `hole_ml`.

### Recovered one-off steps

Three steps of the original chain were run as inline code and never saved as scripts. Their
code was recovered from the original development session logs and is reproduced line for
line in two new files:

- `src/filter_feature_tables.py`
  - m2 to m2f (2026-09-02 02:18 UTC): keeps the column list of the v7 model
    (`champion_v7_CV0.2139/` in the original tree), in v7 order, with `uid` first and the
    label last. This drops `hole_ml` from the rich table and reorders the columns. The two
    v7 header lines ship as `configs/feature_columns/features_v{13,4}_reg7f.header.csv`.
  - m2f to m2fnh (2026-09-03 04:29 UTC): re-reads each m2f table and drops `head_ml`. The
    CSV round trip is kept because the archived m2fnh files were written from the re-read
    text.
  - Added guard: the script exits 1 if `features_v4_m2.csv` is not a column subset of
    `features_v13_m2.csv`. `cache3.py _m2` and `make_regfeat32.py` write that same file
    name, one in the canonical frame and one in the registered frame.
- `src/linear_oof.py` (2026-09-03 04:27 UTC): for each fold, `train_final3.fit_lin` on the
  m2f tables without the columns in `DROP`, `SCANNER` and `{'head_ml'}`. It writes `y` as a
  float, leaves the predictions unclipped and fills `gbm` and `mlp` with NaN. The original
  also computed a diagnostic variant that kept `head_ml` and printed one extra line.
  Neither reached the disk, and both are omitted.

## Deviations and limits

- **Frozen template.** 02 does not rebuild `template_v6.npy`. It copies the released file
  and pins its sha256. The template is a label-free average of the training crops, written
  on 2026-07-25 by `src/register3.py` with its default arguments (three passes of
  registering every crop to the running mean). Run by hand on the stage-04 cache
  `outputs/crops_v3_b.npz`, `register3.py` rebuilds it byte for byte
  (`docs/REPRODUCIBILITY.md`, section 4). The template lives in log1p(SBR) space, and `regfit` applies
  log1p to each crop before fitting, so a template in another intensity space would make
  the NCC meaningless without raising an error.
- **Header-only `features_v4_reg7f.csv`.** The original was the full 2.3 MB v7 table.
  `make_regfeat32.py` reads it with `nrows=2` and uses only the column names. The header
  line hash equals the original's (`72ab84ef…`).
- **Worker count and log path.** `REFEAT_JOBS` defaults to 3. The original used 4. Preprocessing
  and feature extraction run per scan, so only the runtime changes. The log moved from
  `outputs/regfeat_m2.log` to `outputs/logs/regfeat_m2.log`.
- **Added checks.** The subset guard in `filter_feature_tables.py`, the 235/94 assertion
  and the `exported: L1 kept` check in `03_linear.sh`, and the loop that unsets `DAT_*`
  variables are not in the original chain.
- **`hole_ml` and `head_ml`.** `train_final3.SCANNER` withholds `native_spacing`,
  `inner_ml`, `ref` and `head_ml` and keeps `hole_ml`. The m2-to-m2f filter is what removes
  `hole_ml`. Fitting `train_final3.py` directly on an m2 table would give lin 236 features,
  which the assertion in 03 rejects. `DAT_ADMIT_HEAD_ML=1` would re-admit `head_ml`, and
  03 unsets it.
- **LightGBM threads.** `num_threads=4` is hard-coded in `src/train_final3.py` and was
  left unchanged. `OMP_NUM_THREADS=3` matches the original environment.
- **Other backends.** Byte identity was shown on the development hardware class (Apple M3
  Pro, registration on MPS) with the versions in `requirements-train.txt`. Registration on
  CUDA or CPU was not tested here. The registration optimiser runs on the device, so small
  per-scan feature differences are expected elsewhere (the original build's parity gate
  measured a mean of about 7e-4 in probability between MPS-built features and CPU or CUDA
  inference), and the L1 support may change slightly. On other backends the outputs are
  expected to agree with the originals within that tolerance, with different hashes.
- **scikit-learn version.** scikit-learn 1.9 warns that `penalty=` is deprecated and will
  be removed in 1.10. `train_final3.fit_lin` passes `penalty='l1'`, so the training
  environment needs scikit-learn below 1.10 (`requirements-train.txt` pins 1.9.0).
- **joblib warning.** Under CPU contention joblib printed "A worker stopped while some
  jobs were given to the executor" once during preprocessing. The run had 0 failures and
  identical outputs.
- **File name collision.** `cache3.py <tag>` and `make_regfeat32.py --narrow
  features_v4_<tag>.csv` can write the same file. Stage 04 runs only the `_b` and `_f2`
  tags, so the pipeline never collides. The filter guard catches a stray `cache3.py _m2`
  run.
- **Data terms.** `outputs/folds.csv` and the OOF files contain uids and labels. They are
  regenerated locally and are not distributed (`outputs/` is git-ignored).

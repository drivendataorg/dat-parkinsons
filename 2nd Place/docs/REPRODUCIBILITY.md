# Reproducibility

The stages of this pipeline reproduce the scored submission to different degrees. This
document orders them from the strongest guarantee to the weakest and gives the evidence
for each. File names, sizes and hashes of the scored archive are in `docs/PROVENANCE.md`.

Unless a section says otherwise, every measurement below comes from the development
machine: an Apple M3 Pro laptop (11 CPU cores, 18 GB unified memory, macOS, PyTorch MPS, no
CUDA) running the training environment of `requirements-train.txt` (Python 3.12.11,
torch 2.13.0, numpy 2.5.1, scipy 1.18.0, scikit-learn 1.9.0, pandas 3.0.5).

| level | scope | guarantee | main evidence |
|---|---|---|---|
| 1 | Inference from the released weights | Exact in the platform-pinned environment, within 4.0e-6 in the training environment | Max absolute difference to the pre-upload predictions on 150 scans |
| 2 | Stages 01 to 03 and the TabICL stage 07, from raw data | Byte-identical files on the development machine, frozen TabICL contexts prediction-identical | sha256 of every regenerated table, recipe and linear model, max absolute difference 0.0 for the contexts |
| 3 | CNN caches (stage 04) and CNN training (stages 05 and 06) | Caches byte-identical across rebuilds and content-exact against the lost originals. On MPS a complete retrain gave all 52 checkpoints tensor-identical to the scored ones. Seed spread on other devices | Cache hashes, normalisation constants, OOF replays, retrained state tensors |
| 4 | Frozen inputs | Not regenerated by the pipeline. The registration template is rebuilt byte-identically by `src/register3.py` | Pinned sha256, two template rebuilds on MPS |
| 5 | Stacking and packaging (stages 08 and 09) | Byte-identical configuration. 82 of 82 archive entries with equal CRC32 when fed the archived inputs, 52 of 82 after a complete retrain, with the other 30 prediction-identical | Stage 08 and 09 test in an isolated copy, complete `MODE=full` run |
| 6 | Untested cases | None | |

A complete `MODE=full` run of `pipeline/train_all.sh` from the raw data, in a clean copy of
the released code archive (section 5), reproduced the scored package on the development
machine. All 52 CNN checkpoints came out tensor-identical, the stacker and
`inference_config.json` byte-identical, and the rebuilt package predicted the 150-scan
verification set exactly as the scored package (maximum absolute difference 0.0).

## 1. Inference from the released weights

The reference is the set of predictions written on 2026-09-14 by the pre-upload check of the
v17 package. That check ran the v17 code on the CPU over the 150-scan local verification
set, with the platform's library versions (torch 2.12.1, numpy 2.2.6, scipy 1.15.3,
scikit-learn 1.8.0, pandas 3.0.3) loaded from overlay directories, and took 530 s. The
verification scans and the reference predictions contain scan ids and are not distributed.

The unmodified v17 inference code, run in fresh environments on the CPU of the development
machine, reproduced those predictions as follows.

| environment | versions | max absolute difference | wall time, 150 scans |
|---|---|---:|---:|
| `requirements-inference.txt` (platform-pinned) | Python 3.12.11, torch 2.12.1, numpy 2.2.6, scipy 1.17.1, scikit-learn 1.8.0, pandas 3.0.3 | 0.0 | 16 min 57 s |
| `requirements-train.txt` (training) | Python 3.12.11, torch 2.13.0, numpy 2.5.1, scipy 1.18.0, scikit-learn 1.9.0, pandas 3.0.5 | 4.0e-6 | 12 min 59 s |

The platform-pinned environment differs from the competition runtime in one package. The
runtime (Linux x86_64) ran scipy 1.15.3, and the scipy 1.15.3 wheels for macOS arm64 fail
to load on recent macOS. `requirements-inference.txt` therefore pins scipy 1.15.3 on x86_64
only and scipy 1.17.1, the runtime lockfile's pin for other machines, everywhere else.
`requirements-inference.lock.txt` pins every package, dependencies included, of the
platform-pinned environment in the first row of the table (`uv pip freeze`, macOS arm64).

The released weights bundle carries the 18 TorchScript files without their `*.debug_pkl`
records. Original and scrubbed files give bit-identical outputs (`docs/PROVENANCE.md`,
section 3), so the result above holds for either source of weights.

CUDA inference was not tested locally. The only GPU evidence is the scored run itself:
DrivenData's runtime (1× NVIDIA A100 80 GB) completed it and the platform scored it at
private log loss 0.2731. The log of the earlier submission 322341 (2026-09-14) reports
torch 2.12.1+cu129 and CUDA 12.9 in that runtime. The job log of submission 322397 was not
kept, so there is no record that every CNN member ran on the GPU. The inference code
degrades without stopping: a scan that fails preprocessing receives the prior 0.5485, a CNN
failure drops that member and every member after it in the loop for the whole block and
renormalises the stacker over the rest, and a registration failure makes the whole block
fall back to the canonical frame. Each case prints one static warning line. A new
environment should be checked by reading the log for warnings and comparing its
predictions with a CPU run. The size of CPU versus CUDA
differences was never measured. Registration fits each scan with Adam through
`grid_sample`, so a scan close to the NCC 0.30 rejection threshold could change side.

**Order and batch effects.** On the normal path each scan's prediction uses only that
scan's voxels and the frozen model files. The registration objective is a sum of per-scan
terms, the rejection threshold is a fixed per-scan NCC value, and all normalisation
statistics are frozen from training. The code registers scans and runs the CNNs in blocks
of up to 128 scans, so the floating-point summation order inside those batched kernels
depends on which scans share a block. On the 150-scan local set, shuffling the input order
changed predictions by 9e-6 on average and by at most 1.3e-3. Predicting five scans one at
a time changed them by at most 3.1e-4. In a separate check in a fresh environment, one scan
predicted alone differed by 1.5e-5 from the same scan in a 20-scan batch, and a two-scan
folder differed from that batch by at most 4.4e-5. The error fallbacks above act on a whole
block of up to 128 scans, so one scan's failure can change the predictions of the other
scans in its block. None of their warnings appeared in the local runs.

**Memory and time.** Peak resident memory on the M3 Pro CPU (macOS `/usr/bin/time -l`) was
2.2 GB for one scan and 2.7-3.6 GB for runs of 20 to 150 scans. For the 150-scan run macOS
also reported a peak memory footprint of 4.8 GB, which counts compressed pages. On
2026-09-28, on an idle machine with memory to spare, the scored and the rebuilt package
(section 5) peaked at 5.1-5.2 GB resident and 4.8-5.0 GB footprint on the same 150 scans.
Scans are processed in blocks of up to 128, so allow about 8 GB. On an otherwise idle machine
the 150-scan run took 512 s in the platform-pinned environment with the default thread count,
and its predictions differed from the 3-thread run by at most 2.2e-8. With 3 threads it took
497-503 s on 2026-09-28.

Predictions through the shipped `TabularAdapter` on the 1,362 training rows differ from the
scored contexts by 0.0 for the raw model, the log model and their blend. The in-sample log
loss is 0.113362 and the AUROC 0.993002 for both.

The pickle bytes differ by design. When torch pickles a tensor it writes a per-process
serialisation id, and the same tensor pickled in two processes gave different bytes.

The contexts were frozen in the training environment. The original freeze ran with the
platform's library versions. States frozen in the training environment were then loaded and
run in the platform-pinned environment of section 1 (numpy 2.2.6, scikit-learn 1.8.0,
torch 2.12.1, scipy 1.17.1, pandas 3.0.3), and their predictions differ from the scored
states by 0.0. Freezing inside that environment was not tried.

Conditions attached to this result:

- **`PYTHONHASHSEED=1`.** tabicl 2.2.0 orders its ensemble groups with
  `list(set(norm_methods))`, so the order follows Python's string hash seed and decides the
  float32 summation order of the ensemble average. The original freeze set no seed and got
  `['none', 'power']`. An unseeded rerun got `['power', 'none']` and moved predictions by up
  to 6.9e-7 (mean 4e-8). `07_tabular.sh` runs the freeze with `PYTHONHASHSEED=1`, which gives
  `['none', 'power']`. `freeze_tabular.py` records the order in `persistence_checks.json` and
  warns when it differs.
- **numpy `argsort` tie order.** The feature selector has 63 non-zero coefficients, so the
  64th selected column (index 63) is a tie among zero coefficients. The step that grew
  `feature_order` from 235 to 261 names picks 5 zero-coefficient columns the same way (its
  selector has 59 non-zero coefficients). numpy's default `argsort` breaks these ties, and
  `kind='stable'` gives a different pick. The ties reproduce on the development machine
  (arm64, numpy 2.5.1). numpy's SIMD sorts on x86 CPUs with AVX2 or AVX-512 may order them
  differently, which would change `features[63]` (with `median[63]`, `log_prep[63]` and
  column 63 of the context) and part of `feature_order[235:261]`. `prepare_info.json` reports
  the positions of zero-coefficient picks, and `tabular/verify_prepare.py` detects any change
  against the scored recipe. The code keeps the original `argsort` on purpose.
- **Row order.** The context rows follow the order of `features_v13_m2fnh.csv`, and the
  1,148-row subset draws positions with `default_rng(16000)` within each sorted group. A
  feature table with the same values in another row order selects a different subset. Stage
  02 reproduces the original order.
- **scikit-learn below 1.10.** The four prior models and the selector are L1 logistic
  regressions as in section 2.1. scikit-learn 1.9.0 warns about `penalty` and about
  `l1_ratio`, and the non-zero counts and the recipe are unchanged.


The defaults are the `aligned` volumes of `crops_v3_b.npz`, 3 passes of registration to the
running mean, 6 degrees of freedom, unweighted NCC and 120 then 80 Adam steps. The two
arguments only rename the outputs, so that the released template is not overwritten. The run
took 518 s with a peak resident memory of 2.25 GB. The rebuilt file has the sha256 of the
scored asset (`4d3629d5…`), and 0 of its 110,592 voxels differ. The final fit of the run
reported a mean NCC of 0.7884 and a mean rotation of 12.91°, the values the development notes
of 2026-07-25 record for the original registration (0.788 and 12.9°).

The rebuild was repeated on 2026-09-28 in the clean copy of section 5, with its fresh training
environment, from that copy's own `crops_v3_b.npz`. It gave the same sha256, the same mean NCC
and mean rotation, and took 484 s with a peak resident memory of 2.6 GB.

`register3.py` was modified 14 minutes after the template was written. The rebuild shows that
the shipped version with its defaults reproduces the template on the development machine. It
does not show what that modification changed. The fit runs Adam through `grid_sample`, so on
CUDA or on the CPU expect small differences in the rebuilt template. Stage 02 does not rebuild
the template. It uses the released copy and checks its sha256. The same template ships in the
v6, v11, v12a, v12b, v13c, v14c and v17 archives.

## 6. Untested cases

- **CUDA.** Training on CUDA was never run. Inference on CUDA ran only as the scored platform
  submission, without a kept log.
- **CPU-only training.** Never run.
- **Windows.** Nothing was run on Windows, inference included.
- **Linux.** No local run. The only Linux run is the scored platform run.
- **scipy 1.15.3 on the development machine.** Its macOS arm64 wheels do not load, so the
  local inference check used scipy 1.17.1.
- **`MODE=full` on another machine.** The complete retrain ran once, on the development
  machine (MPS). On CUDA or the CPU the CNN weights will differ within the seed spread
  (section 3.2).
- **Freezing the TabICL contexts with the platform's library versions.** Only loading and
  predicting in that environment was tested.
- **x86 CPUs for stages 02, 03 and 07.** The `argsort` tie order, the liblinear L1 support and
  the registration of the training tables were checked only on the development machine.
- **Rebuilding `template_v6.npy` on other devices.** The byte-identical rebuild ran on MPS
  only (section 4).
- **Test-set scale on the CPU.** CPU inference was timed and its memory measured on at
  most 150 scans (section 1). Its time and memory on a test set of the competition's size,
  against the platform's 3-hour limit, were not measured. At 3.3-6.8 s per scan, 1,000
  scans would take about 1-1.9 h.
